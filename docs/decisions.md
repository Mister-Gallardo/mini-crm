# Решения и допущения

## Где ТЗ допускало варианты

1. **SPA на Vite, без серверного слоя.** По ТЗ права должны работать даже при запросах в обход интерфейса, поэтому вся защита живёт в базе. Серверный рендеринг ничего бы к ней не добавил.
2. **Роль хранится только в `profiles`.** Профиль создаётся триггером при добавлении пользователя, по умолчанию с ролью «исполнитель». Постановщиком пользователя делает администратор: меняет `role` в таблице `profiles` через дашборд или SQL, сид делает это сам. Пользователь не может изменить роль себе или другим: прав на запись в `profiles` у клиентов нет. `app_metadata` для этого не подошла: Supabase Auth записывает её уже после создания пользователя, и триггер её не видит. Это исправление вынесено в отдельную миграцию `profile_roles`.
3. **Правила переходов — данные, а не код.** Таблица `task_status_transitions` хранит, из какого статуса в какой, кто (постановщик или назначенный исполнитель) и нужен ли комментарий. По ней работают и проверка в базе, и кнопки в интерфейсе. Новый переход — одна строка в миграции.
4. **Статус меняется только через `change_task_status`.** Прямой `UPDATE` колонки `status` закрыт правами на колонки, при создании задачи статус всегда «Новая». Функция блокирует строку задачи, поэтому два одновременных запроса не проведут один переход дважды. Supabase Security Advisor помечает её предупреждением 0029 (SECURITY DEFINER доступна вошедшим пользователям). Так и задумано: это единственная точка входа, все проверки внутри, `search_path` пустой.
5. **История защищена с трёх сторон.** У клиентов нет прав писать, менять и удалять её: записи создают только функции базы. Внешний ключ на таблицу правил не даёт записать несуществующий переход, а проверка в таблице не даёт вернуть на доработку без комментария даже администратору. Автора и время ставит база.
6. **Создание задачи тоже попадает в историю** (переход «— → Новая»): ТЗ приводит его в таблице переходов.
7. **Принять или вернуть задачу может любой постановщик**, не только её автор.
8. **Исполнителем назначается только пользователь с ролью «исполнитель».** Проверка в базе.
9. **Постановщик может редактировать и переназначать задачу в любом статусе**, статус при этом не меняется. Прежний исполнитель после переназначения задачу больше не видит.
10. **Удаление.** Задача удаляется вместе со своей историей: история — часть задачи, а отдельно её удалить нельзя. Объект с задачами удалить нельзя: это ограничение базы, в интерфейсе кнопка неактивна.
11. **Сотрудники видят имена и роли друг друга.** Это нужно для истории и выбора исполнителя. Email и другие данные учётных записей в API не попадают.
12. **Комментарий спрашиваем только там, где он обязателен** (возврат на доработку). База принимает комментарий к любому переходу, если понадобится.
13. **Ошибки базы приходят кодами** (`transition_not_allowed`, `comment_required` и т. п.), а интерфейс переводит их в понятный текст.

## Что не успел или сознательно отложил

- Переназначение и правки задачи в историю не пишутся: по ТЗ история фиксирует только статусы.
- Нет уведомлений и обновления в реальном времени (Supabase Realtime): данные обновляются после действий и при переходах между экранами.
- Нет поиска, фильтров и пагинации: при текущем объёме они не нужны.
- Нет архива (мягкого удаления) объектов и задач.
- Тестами покрыта база (50 pgTAP-проверок прав и переходов); e2e-тестов интерфейса нет.
- Пользователями управляют через дашборд Supabase или `pnpm seed`, отдельного экрана нет.
